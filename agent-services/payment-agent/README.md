# Payment Agent authentication integration

The agent reuses the application's JWT. Flutter reads the existing `ResidentSession` through `AuthService`; the agent forwards `Authorization` unchanged to .NET. .NET validates the signature, issuer, audience and expiry and resolves the active resident using signed `residentId` and `tenantId` claims. `/chat` validates the session through `/api/v1/auth/me` before calling Gemini, including greeting/help requests.

## Running locally

1. Run the existing .NET backend on port 5073 with its existing Supabase connection and user-secrets. No migration or database change is needed for this integration.
2. Keep `GEMINI_API_KEY` in this folder's ignored `.env`. `BACKEND_API_URL` defaults to `http://127.0.0.1:5073/api`. Do not put JWT or Stripe secrets in the agent.
3. From this folder run `venv\Scripts\python.exe -m uvicorn main:app --host 0.0.0.0 --port 8001` for Android emulator access.
4. Log in again: older resident JWTs without explicit resident claims are rejected. Open **Payments → chat icon** in Flutter.

Flutter defaults to `10.0.2.2` on Android and `localhost` on web. Override with `--dart-define=PAYMENT_API_URL=.../api` and `--dart-define=PAYMENT_AGENT_URL=...`. For Flutter web, set `PAYMENT_AGENT_ALLOWED_ORIGINS` to the exact comma-separated frontend origins. Use HTTPS URLs outside local development.

The chat request body is now:

```json
{"message":"Show my pending invoices","local_time":"2026-09-28T09:00:00"}
```

Send the session JWT in `Authorization: Bearer <JWT>`. Body fields `resident_id` and `token` are rejected. Missing, invalid or expired tokens return 401; non-resident sessions return 403. Backend outages return an error, never an invented zero balance.

## Identity and compatibility

- `JwtTokenService.CreateToken(UserAccount)` remains unchanged for admin/technician logins. Explicit Resident accounts resolve to exactly one active Resident with matching tenant and email; resident IDs never come from UserAccount IDs. Google login preserves the existing account validation and returns a separate resident DTO when applicable.
- The existing passwordless resident dev-login remains available only in ASP.NET's Development environment. It is not a production authentication route.
- Flutter's existing Firebase contact/token exchange calls reference backend routes absent from this checkout. This change does not introduce a replacement authentication system. Production resident login requires the existing verified login path and an explicitly linked Resident-role account; admin accounts cannot be used as resident sessions.
- `/auth/me` resolves residents separately. Payment actions also reject inactive accounts and old resident tokens. Lists ignore a resident's supplied `residentId`; object lookups return 404 for someone else's records.
- Apartment admins are scoped through Residents.TenantId, not Invoice.ApartmentId (which identifies a unit). SuperAdmin retains global access. React payment pages use the existing `ah_token` session.
- Invoice writes, monthly generation, reports and payment verification require an admin role. The unsafe legacy `/api/payments/create` demo route returns 410 for admins and is forbidden for residents. The existing Stripe endpoints are retained.

## Payment behavior

Gemini returns only an allow-listed intent. All financial replies/cards are generated by deterministic read-only tools using paginated .NET responses. Apparent card details/credentials are rejected before classification; do not enter secrets in chat.

`Invoice.canPay` is computed from the invoice and its payments, with no schema column. Successful/Verified transactions exclude an invoice from the payable balance. Successful payments awaiting admin verification remain Pending invoices and have no Pay Now action.

Chat Pay Now rechecks the invoice and opens the existing `CardPaymentScreen`/Stripe PaymentSheet. .NET retrieves Stripe's PaymentIntent, checks invoice ownership, success, amount and currency, and records Successful. Admin verification then sets Verified/Paid and creates the receipt. Repeated intent creation uses a Stripe idempotency key; repeated confirmation returns the existing payment. The agent cannot call write/verification tools.

## Repeatable verification

From the repository root:

```powershell
dotnet build backend/ApartmentManagement.Api
dotnet run --project backend/PaymentSecurity.Tests -- agent-services/payment-agent/venv/Scripts/python.exe
```

The integration executable runs the real JWT middleware/controllers with queryable fixtures and a mocked Stripe HTTP client. It does not start production migrations, create a database, contact Supabase, or charge cards. It also checks that the PostgreSQL provider translates the ownership queries. Passing the Python executable runs authenticated natural-language chat requests against that local server. Set `PAYMENT_TEST_LIVE_GEMINI=1` to additionally test live Gemini classification using the local `.env`; fixture JWTs are passed through process environment, never printed.

From this folder: `venv\Scripts\python.exe -m unittest -v test_security`.

From `mobile`: `flutter analyze` and `flutter test test/payment_chat_test.dart`.

From `web/apartment-management-web`: `npm run build`.

The Flutter test mocks HTTP and Stripe's platform channel while exercising chat → Pay Now → existing PaymentSheet methods → confirmation → awaiting verification. A real emulator/device Stripe test-mode checkout and a live Supabase/admin browser check are still required to validate deployment configuration and native payment UI. No real Stripe transaction is performed by the automated tests.
